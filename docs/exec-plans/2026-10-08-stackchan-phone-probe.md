## 1. 목표 (Goal)

지시서가 알아내라고 한 네 가지를 가설 S1~S4 로 놓고 잰다.

| 가설 | 물음 | 재는 것 | 통과 | 조건부 | 실패 |
|---|---|---|---|---|---|
| **S1 기준 신호** | 에코 제거에 넣을 "스피커로 나가는 소리"를 얻을 수 있나 | (가) 마이크 칩 4칸 가운데 스피커 소리가 전기적으로 되돌아오는 칸이 있는지 (나) 없으면 재생하는 PCM 을 늦춰 넣는 방식의 지연과 그 흔들림 | 하드웨어 칸이 있다, **또는** 소프트웨어 기준의 지연 흔들림이 재부팅 5회에 걸쳐 16ms 이하 | 흔들림 16~48ms(통화 시작 때마다 지연을 재서 맞추는 단계가 필요) | 둘 다 못 얻음 |
| **S2 실시간** | 마이크 → 에코 제거 → Opus 압축·해제 → 스피커가 실시간으로 도나 | 에코 제거 한 묶음·Opus 한 프레임 처리 시간, 한 코어 기준 부하, 소리 읽기·쓰기 오류, 내부 메모리 최저 | 부하 60% 이하 · 오류 0 · 내부 메모리 최저 60KB 이상 | 부하 60~85%(가벼운 에코 제거 방식이나 두 코어 나누기로 60% 이하가 되어야 함) 또는 메모리 40~60KB | 가벼운 방식으로도 85% 초과, 또는 오류가 계속 남 |
| **S3 메아리 감소** | 스피커 소리가 마이크로 되들어온 것이 얼마나 줄어드나 | 시험 음성 재생 중 마이크 원음 대비 에코 제거 결과의 감소량(dB), 음량 세 단계, 마이크 포화 비율 | 통화에 쓸 음량에서 25dB 이상 | 15~25dB(최대 음량을 낮추거나 말 차례 누르기를 세게) | 모든 음량에서 15dB 미만 |
| **S4 공존** | 화면·터치·Wi-Fi 와 소리가 함께 도나 | 10분: 루프백 + 에코 제거 + Opus + 화면 갱신 + 터치 읽기 + Wi-Fi 연결·교환기 왕복 | I2C·소리 오류 0, 재부팅 0, 왕복 중앙값 150ms 이하 | 왕복 150~300ms | 오류·재부팅 발생 |

- 수치는 **잠정 합격선**이다(Tab5 Phase 0 의 PL-D8 을 옮기고 S3 칩에 맞게 고친 것 — 결정 SP-D9). 최종 판정은 사용자의 귀다.
- 결과 표기: 넷 다 통과 = **된다** / 실패가 없고 조건부가 있으면 = **조건부로 된다**(포기할 것을 적는다) / S1·S2·S3 중 하나라도 실패 = **안 된다**(여기서 멈추고 알린다).

## 4. 전제·제약

**확인한 사실(2026-10-08, 이 세션에서 소스·기기로 확인)**
- 스택짱 2호기: `/dev/cu.usbmodem31101`, USB 일련번호 `aabbccddee030000`(= MAC `aa:bb:cc:dd:ee:03`), UIFlow2 의 USB(303a:811a). 스트림덱은 살아 있다(`http://192.168.0.171/health` → `ok`, `/mode` → `dots`).
- CoreS3 소리 배선(M5Unified 0.2.23 `M5Unified.inl`, xiaozhi-esp32 `main/boards/m5stack/core-s3/config.h` — 두 곳이 일치): I2S MCLK G0 · BCLK G34 · WS G33 · 스피커 쪽 DOUT G13 · 마이크 쪽 DIN G14. I2C(G12 SDA/G11 SCL): AW88298 `0x36`, ES7210 `0x40`, 확장칩 AW9523 `0x58`(P0 의 2번 비트 = 앰프 리셋 풀기), 전원칩 AXP2101(ALDO1 1.8V = 앰프, ALDO2 3.3V = 마이크 칩 — `M5.begin` 이 켠다).
- M5GFX 0.2.30 은 이 기기를 `board_M5StackChan` 으로 알아본다(자동 인식 코드 있음). 화면·터치·전원 초기화는 CoreS3 와 같은 갈래다.
- esp-sr 2.5.5 에 esp32s3 라이브러리가 있고 `AEC_MODE_VOIP_HIGH_PERF`·`VOIP_LOW_COST` 가 있다. esp_audio_codec 2.5.0 에 esp32s3 라이브러리가 있다. esp_codec_dev 1.6.2 에 AW88298 드라이버가 있다.
- 맥미니에 ESP-IDF 5.5.4 와 xtensa 도구(`~/.espressif/tools/xtensa-esp-elf`), esptool 5.2.0 이 있다. 디스크 여유 118GB.
- 교환기 생존 확인 주소는 지금 200 을 돌려준다.

**참고 구현이 말해 주는 것(하드웨어 기준 신호는 없을 가능성이 높다)**
- xiaozhi-esp32(커밋 `0d576d3`)의 CoreS3 보드: `AUDIO_INPUT_REFERENCE false` — 코드에는 "기준 입력" 갈래가 있지만 이 보드는 꺼 두었다. 마이크 칩 입력은 MIC1·MIC2·MIC3 을 고른다.
- M5Unified 는 CoreS3 에서 MIC3·MIC4 의 전원을 끈다(Tab5·CoreP4X 에서는 "MIC3 = AEC input" 주석과 함께 켠다).
- Espressif 공식 BSP `m5stack_core_s3`(커밋 `f259a6a`): 기준 신호 설정이 없다.
- → 회로도는 읽지 못했다. **기기에서 직접 잰다**(S1 가). 없으면 소프트웨어 기준(S1 나)이 본선이다.

**모른다(이 실험이 답할 것)**
- MIC3·MIC4 칸에 스피커 소리가 전기적으로 들어오는지.
- 송신(표준 I2S)과 수신(4칸 TDM)을 한 포트에서 같이 쓸 때 AW88298 이 그 클럭(프레임당 64 BCLK)을 받아들이는지 — Tab5 의 ES8388 은 받았다. 안 되면 xiaozhi 처럼 수신을 2칸(MIC1 + MIC3)으로 줄인다.
- S3(240MHz, PSRAM 80MHz)에서 에코 제거·Opus 처리 시간. Tab5(P4)는 에코 제거 2.8ms/16ms + Opus 2.5ms/20ms 로 30~37% 였다.
- 작은 몸통(스피커와 마이크가 몇 cm)에서 마이크가 포화하는 음량.

**제약**
- 서보 세로축 5°~85° 밖 금지 → 서보를 아예 쓰지 않는다.
- `secrets.h` 내용(Wi-Fi 비밀번호·토큰)은 화면·로그·채팅·커밋에 내지 않는다. 시험 펌웨어는 Tab5 의 `main/secrets.h` 에서 `WIFI_NETWORKS` 만 경로로 끌어 쓴다(복사하지 않는다).
- `com.devsync.autopush` 가 5분마다 `add -A` 한다 → 산출물 경로는 과제 1 에서 먼저 무시 규칙에 넣는다. git 태그를 만들지 않는다.
- 맥 쪽 도구는 ESP-IDF 를 export 하지 않은 셸에서 `/opt/homebrew/bin/python3` 로 돌린다.

## Global Constraints

- **대상 기기는 스택짱 2호기 하나**: MAC `AA:BB:CC:DD:EE:03`. 포트는 이름이 아니라 MAC 으로 고른다(`tools/sc_ctl.py port`). 올리기 전에는 `esptool read-mac` 으로 한 번 더 확인하고, 아니면 올리지 않는다.
- **스택짱 1호기(`aa:bb:cc:dd:ee:04`)·Tab5 는 건드리지 않는다.**
- 칩·빌드: ESP-IDF 5.5.4, 대상 `esp32s3`, 플래시 16MB, PSRAM 8MB(Quad), CPU 240MHz, 콘솔 USB-Serial/JTAG.
- 음성 형식: 16kHz 모노, 에코 제거 `aec_create(16000, 4, 1, AEC_MODE_VOIP_HIGH_PERF)`, Opus 24kbps·20ms·복잡도 0(Tab5 전화기와 같다).
- 서보·LED·PY32(0x6F)에 쓰지 않는다.
- 비밀: `secrets.h` 내용 출력 금지. 로그에 Wi-Fi 이름은 남기되 비밀번호는 남기지 않는다.
- 산출물(`out/`, `build/`, `managed_components/`, `sdkconfig`, `dependencies.lock`, `main/test_voice.pcm`, `backups/*.bin`)은 git 제외 — 과제 1 에서 확인.
- 진행 안내·보고는 전부 한국어.

## Review Focus

지시서가 암시하지만 과제의 기대값만으로는 놓치기 쉬운 것 다섯.

1. **엉뚱한 기기에 올리는 것** — 맥미니에 Tab5·다른 CoreS3 가 함께 꽂힐 수 있다. → 과제 2·4·8 의 `read-mac` 확인(`&&` 로 묶어 틀리면 올리지 않음).
2. **백업이 깨졌는데 모르고 덮어쓰는 것** — 되돌릴 길이 사라진다. → 과제 2: 크기 16,777,216 · 첫 바이트 `0xE9` · `verify-flash` 통과를 본 뒤에만 과제 4 로.
3. **스피커에서 소리가 안 나는데 수치가 나오는 것** — 기준 신호만 보고 "메아리가 0 이니 잘 줄었다"고 읽는 실수. → 과제 5: "삐" 소리를 낼 때 마이크 칸이 조용할 때의 3배 이상인지 먼저 확인. `aec_metrics.py` 는 마이크 원음이 무음이면 수치를 내지 않는다.
4. **소프트웨어 기준이 메아리보다 늦게 들어가는 것** — 에코 제거는 기준이 먼저 와야 한다. 늦으면 감소량이 조용히 0 에 가까워진다. → 과제 5: 지연을 재서 "기준이 2~20ms 앞서도록" 맞추고, 재부팅 5회에 걸친 흔들림을 기록.
5. **마이크 포화** — 작은 몸통이라 큰 음량에서 마이크가 찌그러지면 감소량 수치가 무의미해진다. → 과제 6: 포화 1% 초과 음량의 수치는 버리고, 마이크 증폭을 낮춘 값으로 다시 잰다(그 자체가 "최대 음량·증폭 제한"의 근거).

- 사람 목소리로 하는 겹쳐 말하기, 실제 통화(상대 기기와 주고받기)의 음질·지연 — 본 펌웨어 단계에서 사용자 귀로.
- 교환기 연결(WebSocket + TLS)과 지터 버퍼가 얹힌 상태의 코어 0 부하. 여기서는 Opus 압축·해제 + 가끔의 HTTPS 요청까지만 봤다.
- 소리를 실제로 내는 조건의 장시간 가동(10분은 음소거 조건), 30분 이상의 열·배터리.
- 소프트웨어 기준(필요 없어짐), 가벼운 에코 제거 + 일반 소리 방식 Opus 의 조합.
- 스택짱을 실제로 둘 자리에서의 값(이번 자리는 맥미니 옆 책상), 사람이 말하는 거리에서의 마이크 크기.
- 이 결과에 대한 독립 검수(만든 쪽과 다른 눈)는 받지 않았다. 수치는 원자료에서 다시 계산해 옮겼다.

**설계에 넘기는 사실**
- 소리 배선·설정은 `firmware/stackchan_phone_probe/main/board_audio.cpp` 가 기기에서 돈 그대로다(수신 4칸 TDM, 송신은 프레임당 BCLK 64 → 앰프 레지스터 `0x06` 의 `[5:4]` 를 `10` 으로).
- 스택: 에코 제거 + Opus 를 한 태스크에서 돌릴 때 약 19KB. Opus 태스크 단독도 약 19~21KB.
- UIFlow2 의 파티션은 16MB 를 꽉 채운다(남는 자리 0) → 스트림덱과 한 플래시에 함께 담으려면 UIFlow2 쪽을 다시 나눠야 한다.
- UIFlow2 가 도는 기기를 **다운로드 모드로** 넣는 소프트웨어 길은 없다(esptool·`machine.bootloader()`·레지스터 조작 모두 USB 가 죽은 채 멈춤) → UIFlow2 위에 다른 펌웨어를 올리려면 사람 손(RST 3초)이 든다. 반대 방향(우리 펌웨어 → 다운로드 모드)은 esptool 자동 리셋으로 된다. 두 펌웨어를 한 플래시에 담아 "부팅할 쪽만 바꾸는" 방식은 이것과 다른 이야기이고 확인하지 않았다.
- `esp_audio_codec` 을 올려도 S3 에는 이득이 없다(어셈블리 최적화는 P4·S31).
