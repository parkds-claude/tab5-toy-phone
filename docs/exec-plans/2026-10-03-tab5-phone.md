## 1. 목표 (Goal)

Tab5 2대가 **서로 다른 장소(다른 Wi-Fi)** 에 있어도, 화면의 통화 버튼 → 상대 기기 벨 → 받기 → **양쪽이 동시에 말하는 음성 통화** → 끊기가 되는 전용 전화기를 만든다. 장소는 집·사무실·외부(핫스팟) 어디든 바뀔 수 있고, 켜면 저장된 Wi-Fi 에 붙어 스스로 대기 상태가 된다. 완료 판정은 §6.

## 2. 비목표 (Non-Goals)

- 영상 통화, 문자, 3자 이상 통화, 녹음·저장.
- 일반 전화·휴대폰 번호로 거는 기능(전화망 연결).
- 기존 스냅부스·포토 액자 펌웨어와 서버 수정. Wi-Fi 칩(C6) 펌웨어 교체.
- 같은 Wi-Fi 안에서의 직통 연결 최적화(항상 교환기를 거친다 — PH-D2).
- 대기 화면에 가족 사진 슬라이드쇼를 겸하는 것(나중 과제).
- 블루투스 이어폰(기기가 지원하지 않음), 이동통신 내장(Wi-Fi·핫스팟만).
- 통화 중 망이 끊겼을 때 같은 통화를 이어 붙이는 것(끊기면 종료 후 대기로 복귀).

## 4. 전제·제약

**검증된 사실**
- 두 기기 모두 ESP32-P4 rev v1.3 · 화면 ST7121. 1호기 MAC `aa:bb:cc:dd:ee:01`, 2호기 `aa:bb:cc:dd:ee:02`.
- 맥북에서 ESP-IDF 5.5.4 빌드·플래시 가능. `sdkconfig.defaults` 필수 설정(rev v1.x 선택, esp_hosted 2.11.x 고정)은 스냅부스 것을 그대로 쓴다.
- 스냅부스의 Wi-Fi 저장소(최대 8개, 신호 센 순 자동 연결, 화면에서 추가)와 Cloudflare 터널 → 맥미니 경로는 실기 검증됨.
- 쓸 라이브러리는 공식 저장소에 실존(2026-10-03 확인): `espressif/esp_codec_dev`, `espressif/esp-sr` 2.5.5, `espressif/esp_audio_codec` 2.5.0(2.6+ 는 P4 rev 3.0 이상 전용), `espressif/esp_websocket_client` 1.8.0, PyPI `aiohttp` 3.14.3. `esp_codec_dev` 최신은 2.0.0 시험판이라 안정판 1.x 로 고정한다(버전은 Phase 0 에서 확정).
- 공개 선례(xiaozhi Tab5 보드): 스피커 ES8388 은 표준 I2S, 마이크 ES7210 은 4칸 TDM 으로 받고 **0번 = 마이크, 1번 = 에코 기준 신호**. 송수신 동시 동작.

**아직 검증 안 된 가정 — Phase 0 에서 먼저 확인**
- **H1** 화면(M5Unified)과 소리(esp_codec_dev)가 같은 I2C 버스·I2S 를 충돌 없이 함께 쓴다. → 결과: 통과 — 30분 동시 가동에서 오류·재부팅 0. 30분 뒤 터치와 사용자 관찰(울림 등)은 미확인(2026-10-03)
- **H2** 스피커폰 상태에서 에코 제거가 통화 가능한 수준이다. → 결과: 통과 — 잔향 감소 29.4dB(음량 80)·35.9dB(100), 귀 판정 "에코 거의 안 들림·본인 목소리 또렷함"(음량 80 녹음 한 쌍, 맥북 스피커로 청취)(2026-10-03)
- **H3** 맥미니 교환기를 거친 입→귀 지연이 500ms 이하다. → 결과: 망 왕복 어림만 확인(중앙값 92.6ms). **입→귀 지연 자체는 미검증** — Phase 4 에서 측정(2026-10-03)
- **H4** 에코 제거 + Opus 압축·해제가 P4 에서 실시간으로 돈다(CPU·메모리 여유). → 결과: 통과 — Opus 복잡도 0 에서 부하 30~37%(무음·방 잡음 입력 기준. 말소리와 화면·통신 부하를 얹은 값은 Phase 3 에서 재측정). 복잡도 5 는 53.6% 로 초과(2026-10-03)

**제약**
- Tab5 는 2.4GHz Wi-Fi 만 된다. 배터리는 약 6시간(공식 수치)이라 상시 대기는 USB-C 전원을 꽂아 쓴다. 켜진 상태에서만 충전된다.
- `secrets.h`·`.env.phone` 내용은 화면·로그·git 에 출력하지 않는다.
- devsync 가 5분마다 자동 커밋한다 → 새 산출물(`server/.env.phone`, 교환기 로그)은 **.gitignore 에 먼저 넣고 푸시한 뒤** 만든다. `firmware/**/build/` 등은 이미 제외돼 있다.
- 1호기는 공장 백업이 없다 → 플래시 전에 현재 상태를 `backups/` 에 통째로 떠 둔다.
  - 정정(2026-10-04): "공장 백업이 없다"는 틀렸다 — 맥미니 `~/tab5-toy-phone/backups/tab5-1_factory_aabbccddee01_2026-09-22.bin`(16,777,216 B, 검사합 OK)에 있다(맥북에는 없다). 플래시 전 통째 백업은 그래도 떴다: 맥북 `backups/tab5-1_photoframe_aabbccddee01_2026-10-04{,_b2,_b3}.bin` 3개(b1·b3 는 맥미니에도, 서로 NVS 구역만 다름 — 사진 액자 펌웨어가 부팅마다 NVS 에 부팅 횟수를 쓰기 때문). 백업 검증은 한 esptool 세션에서 읽기 → verify 로 한다.

### 9.3 교환기 (`server/`)

- `phone_core.py` — 순수 로직. 기기 접속·이탈, 통화 상태(IDLE / RINGING / IN_CALL), 30초 벨 제한, 신호 검증. 네트워크 코드가 없어 pytest 로 바로 시험한다.
- `phone_relay.py` — aiohttp. `GET /healthz`(Bot Dashboard 용), `GET /ws`(WebSocket). `127.0.0.1` 에만 연다. 설정은 `server/.env.phone`(`PHONE_TOKENS`, `PORT`).
  - (2026-10-03 구현 확정) 수신 주소는 환경변수 `BIND`(기본 `127.0.0.1`)로 바꿀 수 있다 — 기기가 맥북 교환기에 LAN 으로 붙는 Phase 2~3 시험 전용(PL-D4). `/healthz` 는 `{"ok": true}` 만 돌려준다 — 터널로 공개되는 주소에 접속·통화 여부를 내보내지 않기 위해서다(PL-D5). WebSocket 압축은 받지 않는다.
- 인증: 접속 요청 헤더 `X-Device-Id`·`X-Device-Token`(주소창 매개변수 금지 — 로그에 남음). `hmac.compare_digest` 비교, 실패 시 401. 등록된 2대 외 거절. 같은 ID 가 다시 붙으면 옛 연결을 끊는다.
- 기록: 시각·기기·통화 길이·종료 사유만. 음성은 어디에도 쓰지 않는다.

### 9.4 신호 규약

| 방향 | 글자 프레임(JSON) | 뜻 |
|---|---|---|
| 기기 → 교환기 | `{"t":"call"}` `{"t":"accept"}` `{"t":"reject"}` `{"t":"hangup"}` `{"t":"ping","n":1}` | 걸기·받기·거절·끊기·생존 확인 |
| 기기 → 교환기 | `{"t":"reject","msg":N}` (N = 1~3) | 문구 N 과 함께 거절(수신거부 메시지). 교환기는 1~99 의 정수만 건네고, 그 밖의 값은 번호 없는 거절로 낮춘다 |
| 교환기 → 기기 | `{"t":"peer","online":true}` | 상대 기기 접속 여부 |
| | `{"t":"ringing"}` / `{"t":"ring"}` | 발신 측에 "상대 벨 울림" / 수신 측에 "전화 옴" |
| | `{"t":"connected"}` | 통화 시작 |
| | `{"t":"ended","why":"hangup\|reject\|timeout\|offline\|lost"}` | 통화 종료와 사유 |
| 교환기 → 기기 | `{"t":"ended","why":"reject","msg":N}` | 문구 N 과 함께 거절로 끝남(양쪽에 간다). 기기는 1~3 만 문구로 읽고 그 밖은 그냥 거절로 본다. 통화 기록에는 번호를 남기지 않는다 |
| | `{"t":"pong","n":1}` | 생존 확인 응답 |

- 음성은 이진 프레임 `[순번 2바이트][Opus 데이터]`. 통화 중일 때만 상대에게 건넨다. 400바이트를 넘으면 버린다.
- 기기는 15초마다 ping. 교환기는 45초 동안 소식이 없으면 연결을 닫고 상대에게 `peer offline`(통화 중이었다면 `ended: lost`)을 보낸다.
- 양쪽이 동시에 걸면, 벨이 울리는 중에 온 상대의 `call` 을 `accept` 로 취급해 바로 연결한다.

**교환기-기기 계약 (2026-10-03 구현 확정 — 교환기 시험으로 고정됨, 펌웨어는 이 계약을 전제로 만든다)**
- `ended` 는 통화에 참여한 **양쪽 모두**에게 간다 — 끊은 쪽·거절한 쪽 포함(PL-D1). 기기는 "끝났다"를 이 응답 하나로 판단한다.
- 벨 울리는 중 한쪽 연결이 끊기면 남은 쪽은 `ended: offline`, 통화 중이면 `ended: lost` 를 받고, 이어서 `peer online:false` 를 받는다(PL-D2).
- `hangup` 은 벨 중에도 유효하다(거는 쪽의 취소, 받는 쪽이 보내도 종료). `accept`·`reject` 는 벨을 받는 쪽만 유효하다.
- 상태에 안 맞는 신호(대기 중의 `hangup`, 통화 중의 `call` 등)와 깨진 글자·모르는 신호는 **응답 없이 무시**된다 — 기기는 응답이 없다고 멈춰 있으면 안 된다.
- **기기 쪽 규칙(call_fsm 이 지켜야 함)**: `hangup`·`reject` 를 보낸 뒤에는 그에 대한 `ended` 를 받을 때까지(또는 3초 시간 제한) 새 `call` 을 보내지 않는다. `ended` 는 "진행 중인 통화·벨이 있을 때"만 소비하고, 대기 상태에서 받은 `ended` 는 버린다. 이유: 끊자마자 다시 걸면 교환기 응답이 `ended` → `ringing` 순서로 오는데, 기기가 이미 "거는 중"이면 앞 통화의 `ended` 를 새 통화의 종료로 오해한다(신호에 통화 번호가 없다).
- 벨이 울리다 거는 쪽이 취소하면 받는 쪽은 `ended: hangup` 을 받는다 — 받는 쪽 화면은 이것도 `timeout` 과 같이 **부재중**으로 센다.
- 음성 프레임은 3바이트 이상 400바이트 이하만 건넨다. 4096바이트를 넘는 프레임을 보낸 연결은 닫힌다. 교환기는 상대 쪽 송신 대기열이 4096바이트를 넘으면 새 음성을 버리지만(PL-D3), 운영에서는 상대가 같은 맥미니의 터널 프로그램이라 망 정체가 여기까지 거의 올라오지 않는다 — **지연 누적을 막는 실질 방어선은 §9.6 의 기기 쪽 수신 대기열 300ms 폐기**다.
- 재접속하면 옛 연결은 닫히고, 그 옛 연결에서 뒤늦게 온 프레임은 버려진다. 재접속 시점에 통화·벨 중이었다면 그 통화는 끝난다(`lost`/`offline`).

### 9.6 소리 경로 세부

- 캡처는 ES7210 4칸 중 0번(마이크)·1번(에코 기준)만 쓴다. 에코 제거 단위(약 32ms)와 Opus 단위(20ms)가 달라 사이에 링버퍼를 둔다.
- 지터 버퍼는 60ms 로 시작해 40~200ms 사이에서 망 상태에 맞춰 조절한다. 프레임이 비면 Opus 의 손실 은닉으로 메운다.
- TCP 가 잠깐 막혔다 풀리면 프레임이 몰려온다. 수신 대기열이 300ms 를 넘으면 오래된 것부터 버려 **지연이 쌓이지 않게** 한다. 송신 쪽도 밀린 프레임(200ms 초과)은 버린다.
- 벨소리와 연결음은 기기에서 만든다(망을 타지 않음). 벨 음량과 통화 음량은 따로 둔다.
- 지연 예상(추정, 미실측): 캡처 20 + 에코 제거 32 + 망 60~150 + 지터 버퍼 60~100 + 재생 20~40 ≈ **200~350ms**.
- 정정(2026-10-04, 참고 구현 조사 결과 — 위 본문은 지우지 않고 덧붙임):
  - "에코 제거 단위(약 32ms)" → **16ms**(VOIP 방식 256표본, Phase 0 실측). 지연 예상의 "에코 제거 32"도 같은 이유로 16 쪽이다.
  - "프레임이 비면 Opus 의 손실 은닉으로 메운다" → esp_audio_codec 2.5.0 의 Opus 해제기가 손실 은닉을 지원하는지 **미확인** — Phase 3 초반에 시험, 안 되면 직전 프레임을 감쇠시켜 반복한다.
  - 지연 예상에 "재생 쪽 I2S DMA(기본 6×240표본)가 최대 90ms 를 더할 수 있음"을 더한다 — Phase 3 에서 쓰는 박자를 캡처에 묶어 억제한다.
  - 정정(2026-10-04, Phase 3a): "벨 음량과 통화 음량은 따로 둔다" → 3a 는 코덱 음량을 하나(100 고정)로 두고 소리마다 디지털 크기(벨 8000 · 연결음 5300 · 종료음 3700)를 정했다. 통화 음량은 3b. 재생 DMA 는 지금 6칸 × 256표본이고 출력 태스크가 소리가 이어지는 동안 **항상 80~96ms 앞서** 쓴다(최종 검수가 드라이버 소스로 확인 — 기기에서 재지는 않았다). 신호음에는 "끄기 뒤 최대 0.1초"일 뿐이지만 목소리에서는 지연에 그대로 더해지므로 3b 의 첫 결정이다.

- 정정(2026-10-05, Phase 3b — 위 본문은 지우지 않고 덧붙임): **실측 지연**. 계획서 `2026-10-04-tab5-phone-phase3b-voice.md` "지연 예산" 표의 합(같은 Wi-Fi, 한쪽 길 약 115ms(95~170) + 에코 제거 내부 지연)과 나란히 적는다. 실측은 `VPING`(마이크 대신 삑을 보내고 상대가 자기 스피커 되먹임 칸을 돌려보낸 것이 돌아올 때까지 = 왕복)이고 **한쪽 길 어림 = 왕복 ÷ 2 + 25ms** 다. 조건이 다르므로 밤과 아침을 따로 적는다.
  - **밤(2026-10-05 02시경, 빌드 `d77ae98`, 스피커 끔, 같은 Wi-Fi·맥북 교환기)**: 1번 방향 왕복 5회 [237, 253, 253, 253, 253] 가운데 253ms → 한쪽 약 151ms, 2번 방향 [285, 301, 285, 285, 285] 가운데 285ms → 약 167ms, `VPING timeout` 0. 지터 버퍼 `v_jb` 는 3분 통화 중 깊이 2~4 / 목표 2~3. 설계 합격선(왕복 80~320ms)은 충족. 최종 검수는 이 값을 한쪽 길 150~185ms 로 판독했다(예산 115ms 는 낙관적이었다 — 지터 버퍼 두 곳이 예산보다 1~1.5프레임 깊었고 TCP 가 작은 패킷을 모아 보냈다는 판독).
  - **아침(08시경, 빌드 `5935ddd`, Wi-Fi 절전을 끈 뒤, 같은 방법)**: 왕복 29·44(두 값은 삑이 아닌 소리를 잡은 무효)·285·573·540·541ms, `jb=8~10/8` → 한쪽 길 **약 0.3초**(왕복 540~573ms → 약 295~312ms). 합격선 80~320ms 는 **미달**. 지터 버퍼 목표가 양쪽 8(160ms)까지 올라가 있었다(관측: 20초 통화에서 지터 버퍼가 다 떨어진 횟수 5회, 아침 맥북 쪽 Wi-Fi 는 2.4GHz 채널 2·주변 2.4GHz 망 14개·맥북↔공유기 `ping` 최대 약 100ms. 이를 컨트롤러가 2.4GHz 혼잡 탓으로 **추정**했다 — 확인된 것은 아님). 절전을 끄기 전에는 더 나빴다(`e40d097`, 왕복 620~701ms, `jb=6/10`·`0/10`).
  - 사용자의 답(점검표 6번 지연): 아쉬운 점으로 "메아리·지연"을 골랐다. 그 시험은 같은 책상에서 한 대의 스피커만 켠 것이라 내 목소리가 상대 기기 스피커에서 약 0.3초 늦게 나와 내 귀에 들렸을 것이다 — 컨트롤러의 판독이며 사용자에게 확인하지 않았다(실제 통화에서는 내 목소리가 돌아오지 않는다. 단 지연 자체는 실제다).
  - **재지 못함**: ② 에코 제거 안의 지연(닫힌 라이브러리) · ④ Opus 알고리즘 지연 · ⑩ 공기. 재생 DMA 가 정말 (칸 수 − 1) × 16ms 만 앞서 쓰는지는 드라이버 소스로만 봤다(`aud_late=0`, 즉 출력이 48ms 넘게 늦은 적은 없다는 것만 기록으로 확인).
  - **정정 세 건의 결과**: ① 에코 제거 묶음 16ms(그대로 — `VOICE ready chunk=256`). ② Opus 손실 은닉: 부품(`esp_audio_codec` 2.5.0)이 해 주지 않는다(README·라이브러리 역어셈블로 확인) → 직전 프레임을 줄여 가며 직접 메운다(PL3b-D7). ③ 재생 DMA 6칸 80ms → 3칸 32ms(PL3b-D4).
  - **정정 네 건(2026-10-05, 이 과제)**: (a) 계획의 지연 예산(한쪽 115ms)은 낙관적이었다 → 실측 밤 150~185ms, 아침 약 300ms. (b) PL3b-D21(계획서 결정 표의 21번 결정 — 앰프를 코드가 끈다)의 이유: "M5GFX 가 부팅 때 앰프를 켜고, M5Unified 가 같은 `M5.begin` 안에서 다시 끈다(켜져 있는 시간은 소스 판독으로 0.3~1초) — 우리 코드가 직접 한 번 더 끈다(이중 안전장치)". 최종 검수 지적 M-1(검수 보고서의 Minor 번호)의 "약 2초 켜져 있고 실패 경로에서는 켜진 채 남는다"는 재검수가 과장으로 판독했다. **실제로 "퍽" 소리가 났는지는 누구도 확인하지 못했다(소스 판독만, 기기 미확인).** (c) 최종 검수가 "출처 미확정"이라 한 밤의 멈춤 네 번쯤(3분 통화에서 150~250ms 의 멈춤)은 Wi-Fi 절전이었을 **가능성**이 있다(확인된 것은 아니다). | 통화 중 망 끊김 | "연결이 끊어졌습니다" + 종료음 | 통화 종료, 재연결 후 대기 |
| 토큰 거절(401) | "기기 등록 오류" | 1분 간격 재시도 |
| 화면·소리 초기화 실패 | 부팅 화면에 오류 | 재시작 가드(횟수는 NVS 에 기록) |

- 정정(2026-10-04, Phase 3a — 위 표는 지우지 않고 덧붙임): **소리 초기화 실패** 때 지금 펌웨어(`5d9935f`)는 화면 표시도 재시작도 없이 **소리 없이 계속 돈다**(시리얼에 `AUDIO FAIL <단계>`, `STAT … audio=0` — 단 `AUDIO FAIL tones` 는 예외로 `audio=1` 로 남는 표시 불일치, 최종 검수 M-3) — 계획 결정 PL3a-D10, 최종 검수 지적 M-2. 이유: 벨이 안 울려도 화면으로 전화를 받을 수 있고, 재시작 반복이 전화기를 못 쓰게 만드는 것을 피함. 비용: 소리가 안 나는 전화기를 알 방법이 시리얼뿐이라 부재중으로 이어질 수 있음. **승인된 위 표와 다르게 한 곳이며 사용자에게 물은 적이 없다.** 탈출구/예정: 3b 첫 빌드에서 "3번까지 다시 켜 보고(`boot_guard`), 그래도 안 되면 소리 없이 계속"으로 바꾼다(컨트롤러 판정 P3A-R10 — 사용자에게 보고하고 이견이 있으면 바꾼다). 화면의 "소리 꺼짐" 표시는 Phase 5. 소리 장치 실패 경로는 기기에서 실행해 본 적이 없다(코드 읽기로만 확인 — M-3).

## 10. 화면·상태 (`docs/design/README.md` §1·§2 준수, 가로 1280×720, 회전 3)

| 화면 | 요소 |
|---|---|
| 부팅/연결 중 | 진행 문구(Wi-Fi → 교환기) |
| 대기 | 상단: 상대 상태(켜짐/꺼짐)·Wi-Fi 배지(누르면 설정)·배터리. 중앙: 큰 통화 버튼(지름 200px 이상). 하단: 부재중 "n건 · 마지막 시각". 거절 문구 안내 "상대: …" 10초(그 밖의 안내는 4초) |
| 거는 중 | "거는 중…" + 연결음 + 취소 버튼 |
| 전화 옴 | 벨소리 + 받기(초록)·거절(빨강) 큰 버튼 2개. 아래 줄에 벨 끄기(끈 뒤 '벨 꺼짐')·메시지로 거절 |

| Wi-Fi 설정 | 스냅부스 화면 재사용(목록 + 비밀번호 자판) |

- 터치 대상은 96px 이상, 주요 버튼은 160px 이상. 색·글꼴은 디자인 토큰을 따른다.
- 대기 60초 뒤 화면 밝기를 낮춘다. 터치하거나 전화가 오면 원래 밝기로.
- 정정(2026-10-04): 위 "대기" 줄의 Wi-Fi 배지는 "상단"이 아니라 **왼쪽 아래**(x 32~272, y 600~696)에 있다 — 계획 단계의 선택이고 사용자가 화면 사진으로 봤다. 상단(왼쪽 위)에는 "N번 전화기" 라벨, 위 가운데에 상대 상태가 있다. 배터리 표시는 Phase 5 의 몫이라 아직 없다.
- 글자는 스냅부스와 같은 방식으로 그린다: 고정 문구와 숫자는 맥에서 Pretendard 로 미리 그려 넣고(`tools/gen_ui_assets.py` 복사), Wi-Fi 이름처럼 바뀌는 글자만 내장 한글 글꼴(efontKR)을 쓴다.
- 정정(2026-10-08, 토이폰 테마 — 위 내용은 지우지 않고 덧붙임): 화면의 **모양**이 바뀌었다. 위 첫 줄의 "`docs/design/README.md` §1·§2 준수"와 "색·글꼴은 디자인 토큰을 따른다"는 이제 **§5 토이폰 테마**(하늘·동산 바탕, 키캡 버튼, 곰·토끼·병아리, 주아체)를 따른다 — 사용자 요청("키치한 폰화면 → 장난감 전화기 + 귀여운 캐릭터들")과 시안 승인. 화면의 종류·요소·버튼 자리·크기 기준(96/160px)·밝기 낮춤은 그대로다. 달라진 것: 글꼴 Pretendard → 주아체, 벨 화면에서는 안내를 그리지 않음(UL-D3), 문구 몇 개("따르릉! 전화 왔어요", "상대 전화기 켜짐/꺼짐", 말줄임표 → `...`). 계획·결과: `docs/exec-plans/2026-10-08-tab5-phone-toy-ui.md`. **2번 기기에만 올렸고(2026-10-08) 통화는 이 화면으로 아직 시험하지 않았다. 1번 기기는 전 화면 그대로다.**

## 11. 시험 전략

- **교환기**: pytest. `phone_core` 는 순수 로직 시험, `phone_relay` 는 가짜 기기 2대로 걸기·받기·거절·무응답·동시 발신·토큰 거절·큰 프레임 폐기·연결 끊김.
- **펌웨어 순수 로직**(`call_fsm`, `jitter_buffer`): 맥에서 빌드하는 단위 시험을 **먼저 쓰고**(TDD) 구현.
- **실기**: `phone_ctl.py` 로 화면 캡처·터치 주입 → 벨/받기/끊기 반복 자동화. 소리는 시험음 재생 + 기기 통계(보낸/받은 프레임, 끊김 횟수, 지터 깊이).
- **사람 귀**: 음질·에코 최종 판정은 사용자가 한다. 자동화할 수 없는 부분임을 보고서에 명시한다.
- **검수 분리**: 구현 뒤 code-reviewer 에이전트가 독립 검토한다.

  - Opus 복잡도는 0 으로 시작. 음질은 사용자 귀 판정을 아직 받지 못함(30분 가동의 메아리가 복잡도 0 경로였음).

  - 맥미니 스냅부스 서버(:5085)가 꺼져 있다(터널은 정상). 켜는 것은 사용자 결정.

**3b(목소리)로 넘기는 것** (최종 검수 "다음 단계" 11항 + 기존 인계. 3b 계획의 첫 과제로)
1. **출력 태스크의 `printf` 빼기**(M-1) — 목소리 공급자를 붙이기 전 필수. 출력 태스크(우선순위 6)가 `TONE` 줄을 직접 찍어, 시리얼 쪽이 느리거나 `shot` 의 긴 줄과 겹치면 50ms~0.36초 멈출 수 있다(신호음은 바뀔 때만 찍어 영향이 작았다). 찍을 것만 남기고 app 태스크(20ms 바퀴)가 찍게 한다.
2. **앞서 쓰는 양**: `DMA_DESC` 6 → 항상 80~96ms 앞서 쓴다. 3으로 줄이는 안(32~48ms) — **3b 첫 결정**(지터 버퍼 깊이와 함께).
3. **공급자 함수의 조건**(`audio_out.h` 의 `source_fn`): 출력 태스크 안(스택 6KB)에서 불리므로 멈추면 안 된다. Opus 해제(스택 약 40KB)는 다른 태스크가, 공급자는 링버퍼 복사만. 시작 때 5묶음을 연달아 요구한다. 이 조건을 `audio_out.h` 주석에 적는다.
4. **I2S 는 송수신을 한 번의 `i2s_new_channel(&cfg, &tx, &rx)` 로**(시험 펌웨어 `board_audio.cpp` 의 `i2s_setup`·`init`) — 따로 만들면 TDM 수신과 클럭을 나누지 못한다. 그때 송신 슬롯이 32비트로 바뀌므로 출력 경로를 다시 확인(PL3a-D7). 송신을 끄지 않는다(마이크가 같은 클럭). 출력 장치만 따로 닫지 않는다. 마이크 증폭은 열고 난 뒤 다시 설정하고 반환값을 확인한다(Phase 0 에서 한 줄 누락 사례). 입력을 열면 `esp_codec_dev` 가 송신을 슬롯 32비트로 다시 설정하고 그동안의 쓰기는 10ms 쉬고 **버려진다** — 그래서 입력까지 전부 연 **뒤에** 출력 태스크를 띄운다(지금 순서 그대로). 묶음 크기 `BLOCK` 256 은 에코 제거 묶음(16ms)과 같다(유지); Opus 는 320(20ms)이라 받는 쪽은 "해제 320 → 링버퍼 → 256 씩 꺼냄".
5. **섞는 코드(`out_task`, 더하고 넘치면 자름)** 는 3a 에서 한 번도 돌지 않았다 — 순수 함수로 빼 맥 시험(M-7). 통화가 끝날 때 `A_VOICE_STOP` 과 `A_TONE_END` 가 같은 할 일에 오므로 목소리 꼬리와 종료음이 겹친다 — 누가 먼저 멈추는지 정한다. **연결음 꼬리와 첫 목소리가 겹친다**: 거는 쪽은 통화가 열릴 때 `A_VOICE_START` 와 `A_TONE_STOP` 이 **한 묶음**(`FSM RINGBACK -> IN_CALL acts=0x180`, `out/p3a_f.log`)으로 오고, `TONE RINGBACK off` 는 그 뒤에 찍히며, 스피커는 멈춤 뒤에도 이미 내보낸 연결음을 최대 약 96ms(6칸 × 16ms — 드라이버 소스로 본 값, 기기에서 재지 않음) 더 낸다. 받는 쪽은 멈춤 명령이 한 단계 앞(`INCOMING -> ANSWERING acts=0x82`)에서 나간다. 겹침을 3b 가 처리해야 한다(예: 목소리 공급자를 멈춤 뒤 몇 칸 늦게 시작). 에코 제거의 기준 신호는 하드웨어 되먹임(ES7210 칸 1)이라 섞인 뒤 소리가 그대로 기준이 된다 — 소프트웨어로 기준을 만들 필요가 없다.
