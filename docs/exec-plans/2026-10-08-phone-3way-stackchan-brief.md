## 1. 무엇을 하나

지금 전화기는 Tab5 두 대가 서로에게만 건다. 여기에 **스택짱을 세 번째 전화기로 넣고, 걸 때 누구에게 걸지 고르게** 한다.

사용자의 말(2026-10-08):
- "지금 맥미니에 스택짱이 연결되어 있어, 여기에도 전화기능을 넣을 수 있는가?"
- "기기 3대로 누구에게 걸지를 결정하면 안되나? 1,2호기 + 스택짱 … 누구에게 전화걸지를 결정해서 연결될 수 있게 하면 안되나?"
- (소리 실험부터 하자는 제안에) "그러자, 새 세션에서 계획수립-코딩을 하자."

### 사용자가 이미 받아들인 것 (이 대화에서 제안했고 반대가 없었다 — 설계서에서 다시 확인받는다)

- 3대가 서로 건다. 대기 화면에 상대 둘이 캐릭터로 서 있고, **각자의 통화 버튼**을 누르면 그 상대에게 건다. 꺼진 상대는 지금처럼 잠들어 있다.
- 전화가 오면 누가 걸었는지 그 캐릭터가 뜬다(지금 구조 그대로).
- 스택짱용 캐릭터를 하나 새로 그린다(로봇을 제안했다). 곰 = 1번, 토끼 = 2번은 그대로.
- 통화 중인 상대에게 걸면 "통화 중" 안내. **셋이 동시에 하는 통화는 만들지 않는다.**
- **스택짱의 소리 실험을 맨 먼저 한다.** 지금 꽂혀 있는 스택짱 2호기에 시험 펌웨어를 올려도 된다 — 올리기 전에 지금 펌웨어를 통째로 백업하고, 끝나면 되돌릴 수 있게 한다. 실험하는 동안 스트림덱이 멈추는 것은 알렸다.
- 일이 서버·Tab5·스택짱에 걸쳐 있으니 **실험 결과 → 설계서 → 사용자 확인 → 구현** 순서로 간다.

### 아직 정하지 않은 것 (새 세션이 설계에서 정하고 사용자에게 묻는다 — 한 번에 하나씩)

1. **[정해짐 2026-10-08]** 스트림덱은 **유지한다**(사용자: "유지하고 올릴 수 없나? 포기하기 아까워.") — 길은 **A. 재부팅으로 오가기**(사용자 선택 "A"): 스트림덱(UIFlow2)은 그대로 두고, 사용자 자료 칸을 줄여 전화기 펌웨어를 같은 플래시에 넣고, 화면 버튼으로 부팅할 쪽을 바꾼다(약 8초). 스트림덱 상태일 때는 전화를 못 받는다(상대 화면에 "잠듦"). "전화가 오면 자동으로 넘어가기"(B)는 써 본 뒤 얹을 수 있게 남긴다. 근거·확인한 것: `2026-10-08-stackchan-phone-probe.md` 진행 로그, 일지 18:20~. (원래 물음: 스택짱 2호기의 스트림덱(StackDeck)을 포기하는가, 재부팅으로 오가게 하는가.) 통화 펌웨어와 스트림덱(UIFlow2 MicroPython)은 한 펌웨어로 같이 돌 수 없다. 플래시 16MB 에 둘을 나눠 담아 오가는 것이 되는지는 확인하지 않았다.
2. **[정해짐 2026-10-08]** 스택짱 전화기는 **사무실**에 둔다(사용자: "스택짱 전화기는 사무실"). 사용자 확인("사무실 맥미니 옆", "가."): **지금 자리(사무실 책상, 맥미니 옆)에 두고 본인이 쓴다. 평소에는 스트림덱이고 통화할 때만 전화기로 바꾼다.** Tab5 두 대는 다른 곳에 둘 예정이다(사용자: "탭5는 다른 곳에 있을 예정임") → 세 전화기가 서로 다른 장소에 놓인다. 지금 Tab5 2번이 사무실에 있는 것은 개발 중이라서다. (원래 물음: 스택짱을 어디에 두고 누가 쓰는가 — 소리 크기·화면 글자 크기의 기준.)
3. 스택짱 캐릭터(로봇 제안)와 화면의 이름표("N번 전화기"를 스택짱은 무엇이라 부를지).
4. 2인치 화면(320×240)의 구성 — 상대 둘·통화 버튼·받기/거절·끊기·음량을 어떻게 담을지. 메시지로 거절·Wi-Fi 설정 화면을 스택짱에도 넣을지.
5. 스택짱의 머리 움직임(서보)·LED 를 벨이나 통화에 쓸지 — 쓰지 않아도 된다(§6 의 안전 각도).

## 2. 다 됐다는 것은

- 세 기기 어느 쪽에서든 상대를 골라 걸고, 받고, 거절하고, 끊을 수 있다. 통화 중인 상대에게 걸면 안내가 뜬다.
- 스택짱에서 양쪽이 동시에 말하는 통화가 되고, 하울링 없이 알아들을 만하다 — **사용자의 귀로 확인**.
- 교환기·Tab5·스택짱의 맥 시험이 통과하고, **세 기기에 실제로 올라가 있다**(사용자에게 "반영"은 기기에 올리는 것까지다 — §7).
- 문서: 설계서·계획서·README·디자인 규칙·용어사전·일지.
- 소리 실험에서 "스택짱으로는 안 된다"가 나오면 거기서 멈추고 사용자에게 알린다(그것도 끝이다).

## 4. 일의 덩어리와 순서

순서는 고정이다: **가 → (결과 보고) → 설계서 → (사용자 확인) → 나·다·라 → 기기**. 가 가 실패하면 나머지는 하지 않는다.

**가. 스택짱 소리 실험 (관문)** — 버리는 시험 펌웨어. Tab5 때의 Phase 0 과 같은 방식이다(`firmware/tab5_phone_probe/`, 가설·판정은 `2026-10-03-tab5-phone.md` 의 H1~H4).
- 알아낼 것: ① 에코 제거에 넣을 **기준 신호**(스피커로 나가는 소리)를 이 보드에서 얻을 수 있나 — 하드웨어로 마이크 칩에 되돌아오는 칸이 있나, 없으면 재생 PCM 을 소프트웨어로 넣어도 쓸 만한가 ② `마이크 → 에코 제거 → Opus 압축·해제 → 스피커`가 실시간으로 도나(CPU·메모리 여유, 오류 0) ③ 메아리가 얼마나 줄어드나(숫자) ④ 화면·터치·Wi-Fi 와 소리가 함께 도나.
- 판정선은 새 세션이 실험 전에 정해 사용자에게 한 줄로 알린다. 결과는 "된다 / 조건부로 된다(무엇을 포기하면) / 안 된다"로 보고한다.
- 올리기 전: **지금 플래시 16MB 를 통째로 읽어 백업**(오늘 Tab5 에서 한 것과 같은 방식 — `esptool read_flash`), 백업 파일은 git 제외 폴더에.

**나. 교환기 — 여러 대, 상대 지정** (`server/phone_core.py`·`phone_relay.py`, 시험 `server/tests/`)
- 등록 기기 2대 고정을 풀고, `call` 에 거는 상대를, `ring` 에 건 사람을 싣는다. 기기마다 다른 기기들의 켜짐/꺼짐을 알린다. 통화 중인 기기에게 걸면 "통화 중"으로 끝낸다. 동시에 서로 다른 두 통화가 있을 수 있는지(3대라 한 통화 + 남는 한 대)도 정한다.
- **옛 펌웨어가 계속 통화되어야 한다**: 1번 Tab5 가 예전 펌웨어일 수 있고 세 기기를 한순간에 다 올릴 수 없다. 상대를 싣지 않은 `call` 은 지금처럼 Tab5 끼리로 처리하는 식의 호환 길을 둔다.
- 교환기는 지금 **실제로 쓰이는 서비스**다. 바꾸기 전에 시험을 먼저 쓰고, 맥에서 가짜 기기들(`server/tools/phone_fake_peer.py`)로 돌려 본 뒤 재시작한다. 재시작 순간 통화가 끊긴다 — 사용자에게 알리고 한다.

**다. Tab5 — 상대 고르기** (`firmware/tab5_phone/`)
- 판단: `call_fsm.h`(누구에게 거는지·누가 걸었는지), `relay_proto.h`(신호), `device_id.h`(지금은 기기 번호 1·2 만 받는다), `ui_layout.h`(지금은 통화 버튼이 가운데 하나). 그리기: `ui.cpp`·`toy.h/.cpp`(캐릭터가 곰·토끼 둘뿐).
- 대기 화면 배치가 바뀐다 = **손으로 검증된 버튼 자리가 바뀐다**. `test_ui_layout.cpp` 를 먼저 고치고, 화면은 기기보다 먼저 `python3 tools/render_screens.py` 로 본다.

## 5. 확인된 사실과 모르는 것

**확인됨(코드·문서를 읽었다)**
- 교환기의 신호: 기기 → `call` `accept` `reject`(문구 번호 가능) `hangup` `ping` / 교환기 → `peer` `ring` `ringing` `connected` `ended` `pong`. 음성은 이진 프레임 `[순번 2바이트][Opus]` 를 상대에게 그대로 건넨다. 벨 30초 제한, 45초 무소식 끊기.
- 소리 형식: 16kHz 모노, 에코 제거는 esp-sr `aec_create(16000, 4, 1, AEC_MODE_VOIP_HIGH_PERF)`(16ms 묶음), Opus 24kbps·20ms·복잡도 0.
- 스택짱 = M5Stack CoreS3 기반: ESP32-S3 듀얼코어 240MHz, 플래시 16MB, PSRAM 8MB, 2인치 320×240(ILI9342C) + 터치(FT6336U), 듀얼 마이크 ES7210, 1W 스피커 AW88298, 전원 AXP2101, 배터리 550mAh, 서보 둘. 사양 정본: `~/Robot/docs/hardware.md`.
- 스택짱 2호기의 백업이 맥미니에 있다: `~/Robot/firmware/factory-backup/stackchan2-factory-2026-08-12.bin`(출하 펌웨어 16MB)·`m5burner-UIFlow2.0-v2.4.4-B-16MB.bin`. 스트림덱 앱: `~/Deskbot/firmware/stackdeck/`(`deploy.py` 로 올린다), 화면 규격 `~/Deskbot/docs/design/stackdeck.md`.
- 맥미니에 ESP-IDF 5.5.4(`~/esp/esp-idf-5.5.4`)와 Tab5 용 `main/secrets.h` 가 있다.

**모른다(실험·조사로 풀 것)**
- CoreS3 에 에코 제거용 기준 신호가 배선돼 있는지(회로도·공식 BSP·xiaozhi 의 CoreS3 보드 설정으로 확인).
- ESP32-S3 에서 에코 제거 + Opus 의 CPU. Tab5(P4)에서는 복잡도 0 으로 30~37% 였고 복잡도 5 는 넘쳤다. S3 는 더 느리다.
- 작은 몸통에서 스피커와 마이크가 가까운 것이 메아리·하울링에 얼마나 나쁜지. Tab5 에서도 한쪽 기기는 결합이 커서 애를 먹었다.
- 앞선 조사(`docs/exec-plans/2026-10-04-tab5-phone-research/audio-reference-diff.md`)의 결론: 공개된 참고 구현 가운데 **두 대가 동시에 말하는 스피커폰을 검증한 것은 없었다**. 스택짱도 선례 없이 직접 재야 한다.

## 6. 지켜야 할 것·함정 (오늘 겪은 것 포함)

**기기**
- Tab5 가 USB 에 2초 보였다 5초 사라지기를 반복하면 **배터리를 빼 달라고 한다**(방전된 배터리 + 맥 포트). 화면이 꺼진 채 응답이 없으면 다운로드 모드다 → 그대로 올리고 `python -m esptool --chip esp32p4 -p <포트> --after watchdog_reset read_mac` 으로 빠져나온다.
- 상대 기기가 다른 곳에서 켜져 있으면(`STAT … peer=1`) **걸기 시험은 그쪽 벨을 실제로 울린다. 사용자에게 먼저 묻는다.**
- Tab5 1번은 집에 있다 → 올리려면 맥북에서 해야 한다. 맥북에 줄 것(같은 바이너리·명령)을 오늘처럼 미리 넘긴다.
- 스택짱: USB 는 **아래쪽(몸통) 포트** 권장. 서보의 세로축은 **5°~85° 밖으로 보내지 않는다**(하드웨어 손상) — 쓸 일이 없으면 서보를 건드리지 않는다. 스택짱 1호기와 XiaoZhi 쪽(`~/Robot/server/`)은 건드리지 않는다.
- 올리기 전 백업, 올린 뒤 실제 화면(스크린샷)과 응답 확인. 시리얼 포트를 열면 기기가 한 번 리셋될 수 있다.

**저장소·빌드**
- `com.devsync.autopush` 가 5분마다 자동 커밋·푸시한다 → **새 빌드 폴더·내려받은 부품·`sdkconfig`·비밀 파일은 만들기 전에 `.gitignore` 에 먼저**. 지금 `firmware/**/build/` 등은 들어 있다 — 스택짱 펌웨어의 새 산출물 이름을 확인한다.
- **git 태그를 만들지 않는다** — 펌웨어 버전 문자열이 `<태그>-N-g<커밋>` 으로 바뀐다(오늘 만들었다 지웠다).
- `secrets.h`·`.env.phone` 의 내용(토큰·Wi-Fi 비밀번호·주소)을 화면·로그·채팅·커밋에 내지 않는다. 스택짱의 토큰도 같다.
- 교환기의 전용 터널만 만진다. **공용 터널 설정(`config.yml`)과 cloudflared 재시작은 금지** — 다른 서비스 20여 개가 끊긴다(`2026-10-03-tab5-phone.md` 의 롤백 절).
- `STAT`·`TUNE` 줄의 모양은 pytest 가 고정한다. 새 값은 줄 끝에 더하거나 별도 줄·명령으로(지금까지의 방식).
- 맥 시험·도구는 ESP-IDF 를 export 하지 않은 셸에서, `clang++ … -isysroot "$(xcrun --show-sdk-path)"` 로(README "맥 단위 시험").

**과정**
- 개발 규칙(`~/CLAUDE.md`): 문서 먼저·함께, 디자인 규칙과 용어사전을 먼저 고친 뒤 구현, 2단계 이상 작업은 `docs/exec-plans/` 에 계획부터, 영향분석, `docs/daily/` 기록.
- 통화 설계서(`2026-10-03-tab5-phone.md`)의 방식: 결정마다 번호·이유·비용·탈출구, 확인한 것과 못 한 것을 가른다, 시험을 먼저 쓴다.

## 7. 사용자가 일하는 방식 (이 대화에서 확인한 것)

- **"반영해줘·올려줘"는 기기에 올리는 것까지다.** 맥에서 그린 그림과 문서에서 멈추고 "막혔다"고 보고하면 안 된다. 사용자의 손이 필요한 일(배터리 빼기, 기기 꽂기)은 **작업 초반에** 분명히 부탁하고 그동안 나머지를 한다.
- 결과물은 100점 기준 95점까지 고치고 검수하기를 되풀이한다. 디자인·화면에 특히 엄격하다. 검수는 만든 쪽과 따로(code-reviewer 등).
- 화면은 시안을 먼저 보여 주면 빨리 정한다(오늘: 시안 → "좋네. 멋져" + 고칠 점 한 가지). 실제 그리기 코드로 만든 그림(`render_screens.py`)을 좋아한다.
- 보고는 쉬운 한국어로, 한 것과 못 한 것을 갈라서. 중간에 오래 말이 없으면 답답해한다.
