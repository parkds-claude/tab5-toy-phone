# 전화기 3대 — Tab5 1·2번 + 스택짱, 거는 상대 고르기 (설계서)

## 1. 목표 (Goal)

전화기를 Tab5 두 대에서 **세 대**(Tab5 1번·2번 + 스택짱 2호기)로 늘린다. 대기 화면에 상대 둘이 서 있고, 걸고 싶은 상대의 통화 버튼을 누르면 그 상대에게 걸린다. 전화가 오면 누가 걸었는지 그 캐릭터가 뜬다. 스택짱은 **스트림덱을 그대로 두고**, 화면 버튼으로 전화기와 오간다.

## 2. 비목표 (Non-Goals)

- 셋이 동시에 하는 통화(회의 통화), 문자, 영상.
- 스택짱에서의 "메시지로 거절"·Wi-Fi 설정 화면(TW-D5), 서보·LED 연출(TW-D6).
- 스트림덱 상태일 때 전화 받기("전화가 오면 자동으로 넘어가기" — 지시서의 B 안. 써 본 뒤 얹을 수 있게만 남긴다).
- 스택짱 1호기, XiaoZhi 쪽(`~/Robot/server/`), 공용 터널 설정.
- Tab5 의 통화음 값 조정(P5A 의 귀 판정은 사용자가 Tab5 1번을 올린 뒤).

## 3. 영향 범위 (Blast Radius)

- **교환기**(`server/phone_core.py`·`phone_relay.py`·`tests/`·`tools/phone_fake_peer.py`·`phone_smoke.py`): 실제로 쓰이는 서비스(launchd `com.example.tab5phone-relay`). 바꾼 뒤 재시작하는 순간 붙어 있던 기기가 1~2초 끊겼다 다시 붙는다(통화 중이면 그 통화는 끝난다). `server/.env.phone` 에 스택짱 토큰 한 줄이 늘어난다.
- **Tab5 펌웨어**(`firmware/tab5_phone/`): 신호 규약·상태 기계·기기 표·대기 화면 배치·캐릭터가 바뀐다. 두 대에 같은 바이너리. 옛 펌웨어의 Tab5 는 교환기가 바뀐 뒤에도 Tab5 끼리 지금처럼 통화한다(§6.4).
- **스택짱 2호기**: 플래시의 칸 나눔(파티션 표)과 사용자 자료 칸(`vfs`)을 다시 쓴다 — UIFlow2 앱·시스템 칸은 그대로. 스트림덱 앱(`~/Deskbot/firmware/stackdeck/main.py`)에 "전화기" 버튼 하나가 늘어난다(Deskbot 저장소 소관 파일).
- **비밀 파일**: `firmware/tab5_phone/main/secrets.h` 의 `PHONE_DEVICES` 에 스택짱 한 줄(맥미니·맥북 둘 다), `server/.env.phone` 의 `PHONE_TOKENS`. 내용은 어디에도 출력하지 않는다.
- **과금**: 없음.

## 4. 전제 — 관문 실험이 알려 준 것

스택짱(M5Stack CoreS3 기반, ESP32-S3)은 **조건부로 된다**(2026-10-08).
- 에코 제거용 기준 신호가 하드웨어로 있다(마이크 칩 칸 1). 배치가 Tab5 와 같다(칸 0·2 = 마이크, 칸 1 = 기준).
- 메아리 감소 32~43dB(통과). 처리 여유는 Tab5 의 3분의 1 → **에코 제거와 Opus 를 다른 코어에**, 에코 제거는 `AEC_MODE_VOIP_LOW_COST`. 그때 코어 1 = 55%, 코어 0 = 49%.
- 내부 메모리가 빠듯하다(Wi-Fi 까지 올린 뒤 40KB, TLS 연결 중 최저 13KB). 스택·에코 제거·Opus 상태는 내부 메모리에 있어야 빠르다.
- 마이크 증폭 12dB(Tab5 의 30dB 는 포화), 음량은 앰프 레지스터 `0x0C` 에 직접(윗 4비트 6dB · 아랫 4비트 0.5dB).
- UIFlow2 가 도는 기기를 다운로드 모드로 넣는 소프트웨어 길은 없다(RST 3초). 우리 펌웨어(USB-Serial/JTAG 콘솔)에서는 esptool 자동 리셋이 된다.
- UIFlow2 의 칸: `factory` 9.56MB(앱 9.02MB) · `sys` 1MB · `vfs` 4.75MB(0.68MB 사용) · `storage` 0.62MB. 부트로더가 `otadata` 를 알고, MicroPython 에 부팅 대상 바꾸기(`set_boot`)가 있다(백업 이미지에서 확인 — 기기에서 해 본 것은 아니다).

## 6. 신호 규약 v2 (정본 — 교환기 시험과 `relay_proto.h` 시험이 고정한다)

### 6.1 접속
- 주소·인증은 그대로: `GET /ws`, 헤더 `X-Device-Id`·`X-Device-Token`.
- 새 펌웨어는 헤더 **`X-Phone-Proto: 2`** 를 더 보낸다. 없거나 `2` 가 아니면 v1 연결이다.
- 등록 기기는 `PHONE_TOKENS="tab5-1:…,tab5-2:…,stackchan-2:…"` — **2~8대**. **옛 짝** = v1 기기끼리의 상대: 환경변수 `PHONE_LEGACY_PAIR="tab5-1,tab5-2"`, 없으면 `PHONE_TOKENS` 에 적힌 순서의 앞 두 대.

### 6.2 기기 → 교환기
| 글자 프레임 | 뜻 |
|---|---|
| `{"t":"call","to":"<기기ID>"}` | 그 기기에게 건다(v2) |
| `{"t":"call"}` | 옛 짝에게 건다(v1 호환. v2 연결이 `to` 없이 보내도 같은 규칙) |
| `{"t":"accept"}` `{"t":"reject"}` `{"t":"reject","msg":N}` `{"t":"hangup"}` `{"t":"ping","n":1}` | 그대로 |

### 6.3 교환기 → 기기
| 글자 프레임 | 받는 연결 | 뜻 |
|---|---|---|
| `{"t":"peer","id":"<기기ID>","online":true\|false}` | v2 | 다른 등록 기기 하나의 상태. 접속 직후 **다른 기기 전부**에 대해 하나씩, 이후 바뀔 때마다 |
| `{"t":"peer","online":true\|false}` | v1 | 옛 짝의 상태(지금과 같다) |
| `{"t":"ring","from":"<기기ID>"}` | v2 | 전화 옴 + 건 기기 |
| `{"t":"ring"}` | v1 | 전화 옴(건 쪽은 옛 짝) |
| `{"t":"ringing"}` `{"t":"connected"}` `{"t":"pong","n":1}` | 모두 | 그대로 |
| `{"t":"ended","why":"hangup\|reject\|timeout\|offline\|lost\|busy"}` (+ `"msg":N`) | 모두 | 종료. **`busy`** 가 새 사유다 — v1 기기는 모르는 사유를 "상대가 받지 않고 끊음"으로 보여 준다(기존 동작) |

- **v2 연결이 보는 상태**: 상대가 v1 로 붙어 있고 내가 그 옛 짝이 아니면 `online:false` 로 알린다(걸 수 없는 상대는 꺼진 것으로 보인다 — TW-D8).
- 음성 이진 프레임 `[순번 2바이트][Opus]` 는 그대로. 같은 통화의 상대에게만 건넨다.

### 6.4 걸기 판정 (교환기, 위에서부터)
1. 거는 쪽이 **벨을 받는 중**이고, `to` 가 없거나 `to` 가 나에게 건 기기면 → 받기로 취급한다(서로 동시에 걸기 — 지금 규칙의 일반형).
2. 거는 쪽이 이미 벨·통화에 묶여 있으면 → 무시(응답 없음).
3. `to` 가 미등록이거나 자기 자신이면 → 무시(`bad_signal`). `to` 가 없는데 옛 짝이 없는 기기면 → 무시.
4. 대상이 꺼져 있거나, 대상이 v1 인데 거는 쪽이 그 옛 짝이 아니면 → 거는 쪽에 `ended: offline`.
5. 대상이 벨·통화에 묶여 있으면 → 거는 쪽에 `ended: busy`.
6. 그 밖 → 벨: 거는 쪽에 `ringing`, 받는 쪽에 `ring`(v2 면 `from` 포함). 30초 제한.

### 6.5 그대로인 계약
`ended` 는 그 통화의 양쪽 모두에게 간다 · 벨 중 이탈 = `offline`, 통화 중 이탈 = `lost` · 같은 ID 가 다시 붙으면 옛 연결을 닫고 그 기기가 묶여 있던 통화는 끝난다 · 상태에 안 맞는 신호는 응답 없이 무시 · 45초 무소식이면 끊는다 · 기록에는 시각·기기·통화 길이·사유만.

## 7. 교환기 (`server/`)
